## 2026-11-04 增量：可选的 debug 记录等级

- 此前 `/api/bridge/logs` 的环里只会产生 `info`/`warn`/`error` 三种行，排查"这个请求到底发给了谁、上游回了什么"时无从下手。现在加入**记录等级阈值**：`telemetry` 只保存不低于阈值的行，默认 `info`（与之前行为一致），`debug` 打开后才产生调试行、也才占用环容量。
- 设置来源三档：`ACCIO_BRIDGE_LOG_LEVEL`（环境变量，启动时优先）→ 配置 `logging.level` → 兼容旧的 `server.logLevel`；运行时用 `POST /api/bridge/logging {"level":"debug"}` 切换，`GET /api/bridge/logging` 读当前值与可选值；非法等级返回 400 并列出 `debug, info, warn, error`。
- `debug` 行覆盖：每次生成的模型与解析后的上游地址（provider / stream / 工具数 / 是否带 key）、上游回执的 status 与 content-type、上游连接失败的原始原因、目录请求（自定义模型数 / 是否取官方目录 / 官方组数）、透明透传的 method-path-status。
- 回归数字：单元测试 44 → **46**（阈值门控 + 读取过滤仍生效）；黑盒 22 → **23**（运行时切换、debug 行出现、切回 `info` 后不再新增、非法等级 400）。本机（Windows / `x86_64-pc-windows-gnu`）`cargo fmt --check`、`cargo test`、`clippy -D warnings`、`release` 构建全通过；`tests/parity.cjs` 23/23；`tests/upstream-stream.cjs` 通过；工作区交叉黑盒 28/28。
- 线上实测：`GET /api/bridge/logging` → `info`；切 `debug` 后一次真实生成产出两条 debug 行（`generate … -> http://127.0.0.1:3425/chat/completions (provider=openai, stream=true, tools=0, auth=none)`、`upstream replied status=200 contentType=text/event-stream`）；切回 `info` 后同样的生成不再新增 debug 行；`?level=info` 的读取过滤仍会隐藏 debug 行。
