## 2026-11-04 增量：官方透传凭据对齐 Node（修复 1688 工作流第一步失败）

- 现象：Accio 启动后 `POST /api/mcp/ali1688/sgcookie` 经网关透传反复返回 **400**，1688 相关的工作流（item-one-click、店铺全景）在"理解意图"第一步即中断。

- 修法：`official_request` 改为 Node 语义——除逐跳头、重新计算的 `content-length`、以及本网关管理令牌 `x-gateway-token` 外全部转发；`authorization` 仍排除等于 `server.token`/运行时令牌的值，配置的 `upstream.apiKey` 优先。
- 回归：单元 46、黑盒 **23/23**、`upstream-stream` 通过（新增断言：`cookie`/`authorization`/`x-accio-token` 必须转发、`x-gateway-token` 绝不转发、网关令牌形状的 Bearer 被丢弃）、工作区交叉黑盒 28/28。

## 2026-11-04 增量：模型路由、工具结束语义与面板安全

- 模型名解析改为分层：此前一次扫过所有名字取首个命中，正式 `id`、`modelCode`、别名、`upstreamModel` 谁先出现谁生效，于是较早模型的别名或上游名会遮住较晚模型真正的 `id`，请求可能被发到调用方没指定的提供商。现在按 正式 `id` > `modelCode` > 别名 > `upstreamModel` 依次匹配，名字仍不区分大小写；同一名字若还有另一个已启用模型应答，记一条告警并点名两个模型。
- 已注册但禁用的模型不再落到官方透传（那里会以无关原因失败），改为直接返回 HTTP 404 `model <id> is configured but disabled; enable it in the gateway panel`。未知名字继续透传官方上游，`/api/bridge/test` 仍回答 `custom model not found`。
- 配置保存校验新增重名拒绝：`modelCode` 或别名等于另一个模型的正式 `id`（两个模型应答同一个名字）时拒绝保存，错误里点名两个模型；多个提供商共用一个 `upstreamModel` 仍然允许。
- 工具调用帧补上上游用量（`usageMetadata`），带工具的轮次与纯文本轮次口径一致。上游因长度/令牌上限或内容过滤中止时，网关改为返回带该原因的 error 并保留用量，不再把只写了一半的调用标成 `finishReason: "TOOL_CALLS"`。有意保持不变：完整但非法的参数文本仍原样交给客户端，由客户端自己报解析错误（旧黑盒用例断言此行为）。
- 内嵌管理面板不再把模型 id 拼进内联 `onclick`/`onchange`。HTML 转义不等于 JavaScript 字符串转义，id 里带单引号就会弄坏按钮，构造过的 id 还能在点击时执行。面板操作改走 `data-model-action` / `data-model-toggle` 属性，由委托监听器处理。
- 面板可以认证了：每项管理调用都经一个包装函数，从内存值附加 `x-gateway-token`，收到 401 时显示令牌输入条。面板页面自身即使 `server.enforceToken` 为真也免令牌（否则索取令牌的页面本身会被挡住），管理路由全部仍然需要令牌，令牌只存内存、不持久化。

## 2026-11-04 增量：上游错误诚实化、单一网络策略、流式解压与令牌能力划分

- 上游错误不再一律 502：自定义模型上游返回非 2xx 时，网关先读取状态、`retry-after`、上游请求 id 与有界响应片段，再把这四样写进客户端可见的 message（例如 `model upstream returned HTTP 429: invalid key *** (type=invalid_request_error, code=invalid_api_key) retry-after=7`），并把上游状态码透传给客户端；只有连不上（传输失败）才仍然是 502。片段经过脱敏（`sk-` 前缀、`name=` 字段、`Bearer <x>`、≥32 位不透明串都被替换），密钥既不进正文也不进日志行。
- 官方目录失败也带上原因：`Official catalogue unavailable` 后面追加同样的状态/原因/重试提示，不再只有一句"不可用"。
- 一条网络策略显式化：`App` 现在有两个客户端——`client` 保留环境代理（官方源与远程提供商），`local_client` 强制 no-proxy（回环地址的模型与本地发现）。此前回环模型是否走代理取决于调用方，而发现流程自己造了 no-proxy 客户端并忽略了传入的那个客户端。
- 流式响应解压：上游 SSE 带 gzip/deflate/brotli（或在缺 header 时按 gzip 魔数识别）时先解码再交给事件解码器；此前压缩流会被当成非法 UTF-8/非法 JSON，整轮只返回一个 error 帧。透明透传路径不受影响，仍逐字节转发 body 与 `content-encoding`。
- 抓包留存：写盘改到阻塞线程池，并按 `ACCIO_BRIDGE_CAPTURE_MAX`（默认 200）只清理自己的 `generate-*.json`，不再无上限增长。
- 令牌能力划分（`server.adminToken`，可选）：留空时是旧的单令牌行为，一个令牌通行全部能力；配置后数据面令牌只保留 inference/catalogue，management/discovery/launch（含 `POST /api/bridge/accio/launch`——启动本机可执行文件）必须用管理令牌。缺凭据 401，凭据有效但范围不足 403；`GET /api/bridge/config` 只回 `server.hasAdminToken` 布尔值，两把密钥都不出现在任何响应体或日志里；面板在 403 时提示需要管理令牌。
- 模型列表探测 `POST /api/bridge/discover/models` 加主机门：只探测回环地址或 `server.discoveryAllowedHosts` 列出的主机，其他主机在建立连接前就返回 403，拒绝信息只含主机名，不回显 URL 与密钥（此前它会把保存的 apiKey 送到调用方指定的地址）。
- 回归数字：单元测试 **78**；黑盒 **36/36**；面板 DOM **13/13**；`ui` **16/16**；旧工作区交叉黑盒 **28/28**；`cargo fmt --check`、`clippy -D warnings` 与 release 构建全通过。
- 两个评审批次各自在独立工作树实现（`review-batch2-upstream`、`review-batch2-auth`）后合并：合并需手工处理"双方在同处追加"的冲突，其中黑盒夹具里旧的无条件 `/api/llm/config/v2` 处理器被删除——它会把新增的 401 分支挡成死代码。
